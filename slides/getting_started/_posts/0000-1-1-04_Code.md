# 1. Le Code Qui Ment 🤥 <!-- .element: class="r-fit-text" -->

---

## Trouvez le problème...

```java
public boolean check(int a, int b, String c) {
    if (a > 0 && b < 150 && c != null && c.length() > 2) {
        return true;
    }
    return false;
}
```

<p class="fragment">❓ Que fait cette méthode ?</p>
<p class="fragment">❓ Que signifient <code>a</code>, <code>b</code>, <code>c</code> ?</p>
<p class="fragment">❓ Pourquoi <code>150</code> ? Pourquoi <code>2</code> ?</p>

---

## Le même code, honnête

```java
public boolean isEligibleForEvent(int balance, int age, String email) {
    boolean hasSufficientFunds = balance > 0;
    boolean isValidAge = age < MAX_AGE;
    boolean hasValidEmail = email != null && email.length() > MIN_EMAIL_LENGTH;

    return hasSufficientFunds && isValidAge && hasValidEmail;
}
```

<p class="fragment">👉 Le code doit <strong>révéler l'intention</strong>, pas la cacher.</p>
<p class="fragment">👉 Un bon nom rend le commentaire <strong>inutile</strong>.</p>

---

## La règle des noms

<ul>
<li class="fragment">❌ <code>d</code>, <code>tmp</code>, <code>data</code>, <code>obj</code>, <code>flag</code></li>
<li class="fragment">✅ <code>elapsedTimeInDays</code>, <code>userWallet</code>, <code>isEventOpen</code></li>

# 2. Value Objects 💎 <!-- .element: class="r-fit-text" -->

---

## Le problème des "Primitives Obsession"

Dans la plupart des codes étudiants :

```java
public void createEvent(String name, int capacity, double price, String organizerEmail) {
    // ...
}
```

Que se passe-t-il si on appelle :

```java
eventService.createEvent("Gala", -50, -10.0, "pas_un_email");
```

<p class="fragment" style="color:#ef5350;">Le compilateur ne dit rien. Le bug arrivera en production. 💥</p>

---

## La Solution : Typer le Métier

Chaque concept métier **important** mérite sa propre classe.

```java
public record Capacity(int value) {
    public Capacity {
        if (value <= 0) throw new IllegalArgumentException("Capacity must be positive");
    }
}

public record Email(String value) {
    private static final Pattern REGEX = Pattern.compile("^[\\w.-]+@[\\w.-]+\\.[a-z]{2,}$");
    public Email {
        if (!REGEX.matcher(value).matches()) throw new IllegalArgumentException("Invalid email: " + value);
    }
}
```

---

## Avant / Après Value Objects

**❌ Avant :**
```java
createEvent("Gala", -50, -10.0, "pas_un_email"); // compile !
```

**✅ Après :**
```java
createEvent(
    new EventName("Gala"),
    new Capacity(-50),        // 💥 IllegalArgumentException ICI
    new Price(-10.0),         // 💥 IllegalArgumentException ICI
    new Email("pas_un_email") // 💥 IllegalArgumentException ICI
);
```

<p class="fragment">👉 L'erreur est attrapée <strong>à la construction</strong>, pas au fond d'un service.</p>
<p class="fragment">👉 C'est la base du <strong>Domain Driven Design</strong> vu précédemment.</p>

# 3. Immutabilité 🔒 <!-- .element: class="r-fit-text" -->

---

## Le problème des objets mutables

```java
Ticket ticket = new Ticket("Alice", "Gala", TicketStatus.PENDING);

// ... 50 lignes plus tard ...
ticket.setStatus(TicketStatus.PAID);

// ... 100 lignes plus tard ...
ticket.setStatus(TicketStatus.CANCELLED);

// Question : quel est l'état du ticket ICI ?
```

<p class="fragment">Plus le code est long, plus suivre l'état d'un objet mutable est <strong>impossible</strong>.</p>

---

## La Solution : On ne modifie pas, on crée

```java
public record Ticket(String holder, String eventName, TicketStatus status) {

    public Ticket pay() {
        if (this.status != TicketStatus.PENDING) {
            throw new IllegalStateException("Cannot pay a non-pending ticket");
        }
        return new Ticket(this.holder, this.eventName, TicketStatus.PAID);
    }
}

// Usage
Ticket pending = new Ticket("Alice", "Gala", TicketStatus.PENDING);
Ticket paid = pending.pay(); // pending n'a PAS changé
```

<p class="fragment">👉 Chaque transition d'état est <strong>explicite</strong> et <strong>validée</strong>.</p>

# 4. Guard Clauses 🛡️ <!-- .element: class="r-fit-text" -->

---

## La "Pyramide de l'Enfer"

Vous connaissez ce code ?

```java
public String processOrder(Order order) {
    if (order != null) {
        if (order.getUser() != null) {
            if (order.getUser().hasWallet()) {
                if (order.getUser().getWallet().getBalance() > order.getAmount()) {
                    // Enfin... la vraie logique est ici
                    return "OK";
                }
            }
        }
    }
    return "ERROR";
}
```

<p class="fragment" style="color:#ef5350;">3 niveaux d'imbrication, impossible à déboguer.</p>

---

## Guard Clauses : Retourner tôt

L'idée : **éliminer les cas d'erreur en premier**, puis écrire la logique principale.

```java
public String processOrder(Order order) {
    if (order == null) return "ERROR: order is null";
    if (order.getUser() == null) return "ERROR: no user";
    if (!order.getUser().hasWallet()) return "ERROR: no wallet";
    if (order.getUser().getWallet().getBalance() <= order.getAmount()) {
        return "ERROR: insufficient funds";
    }

    // Code heureux, sans imbrication
    return "OK";
}
```

<p class="fragment">👉 Le "Happy Path" est toujours à la fin, <strong>au même niveau d'indentation</strong>.</p>

# 5. Single Responsibility 🎯 <!-- .element: class="r-fit-text" -->

---

## Une fonction = une chose

**❌ Mauvais : cette méthode fait 4 choses**

```java
public void handleTicketRequest(String userEmail, String eventId) {
    // 1. Validation
    if (userEmail == null || eventId == null) throw new RuntimeException("Invalid input");
    // 2. Récupération données
    User user = db.findUserByEmail(userEmail);
    Event event = db.findEventById(eventId);
    // 3. Logique métier
    if (user.getBalance() < event.getPrice()) throw new RuntimeException("Insufficient funds");
    user.setBalance(user.getBalance() - event.getPrice());
    // 4. Notification
    emailService.send(userEmail, "Votre billet pour " + event.getName());
}
```

---

## Après décomposition

```java
public void handleTicketRequest(String userEmail, String eventId) {
    validateInputs(userEmail, eventId);
    User user = fetchUser(userEmail);
    Event event = fetchEvent(eventId);
    processPayment(user, event);
    notifyUser(user, event);
}

private void validateInputs(String email, String eventId) { ... }
private User fetchUser(String email) { ... }
private Event fetchEvent(String id) { ... }
private void processPayment(User user, Event event) { ... }
private void notifyUser(User user, Event event) { ... }
```

<p class="fragment">👉 Chaque méthode a <strong>un nom</strong>, <strong>un but</strong>, et peut être testée <strong>indépendamment</strong>.</p>

# 6. TDD : Test Driven Development 🧪 <!-- .element: class="r-fit-text" -->

<img src="../assets/images/tdd.png" alt="TDD Cycle" style="max-width:400px;">

---

## L'approche classique vs TDD

<div style="display:flex; gap:1.5em;">
    <div style="flex:1; background:#c62828; padding:1em; border-radius:8px; color:#fff; font-size:0.85em;">
        <strong>❌ Approche classique</strong>
        <ol>
            <li>J'écris le code</li>
            <li>Je teste à la main dans Postman</li>
            <li>Ça marche... chez moi</li>
            <li>J'écris les tests (si j'ai le temps)</li>
        </ol>
    </div>
    <div style="flex:1; background:#1b5e20; padding:1em; border-radius:8px; color:#fff; font-size:0.85em;">
        <strong>✅ TDD</strong>
        <ol>
            <li>J'écris le test (qui échoue 🔴)</li>
            <li>J'écris le minimum de code pour le faire passer 🟢</li>
            <li>Je refactorise sans casser le test 🔵</li>
            <li>Je répète</li>
        </ol>
    </div>
</div>

---

## 🔴 Red : j'écris le test d'abord

```java
@Test
void should_reject_ticket_when_balance_is_insufficient() {
    // Arrange
    Wallet wallet = new Wallet(5.0);
    Event event = new Event("Gala", new Price(20.0));

    // Act + Assert
    assertThatThrownBy(() -> wallet.pay(event.getPrice()))
        .isInstanceOf(InsufficientBalanceException.class);
}
// Ce test ne compile même pas encore. C'est normal.
```

---

## 🟢 Green : j'écris le minimum de code

```java
public class Wallet {
    private double balance;

    public Wallet(double balance) { this.balance = balance; }

    public void pay(Price price) {
        if (this.balance < price.value()) {
            throw new InsufficientBalanceException("Solde insuffisant");
        }
        this.balance -= price.value();
    }
}
```

<p class="fragment">Le test passe. On ne va pas plus loin pour l'instant.</p>

---

## 🔵 Refactor : j'améliore sans casser

```java
public class Wallet {
    private final double balance; // Immutable !

    public Wallet(double balance) {
        if (balance < 0) throw new IllegalArgumentException("Balance cannot be negative");
        this.balance = balance;
    }

    public Wallet pay(Price price) { // Retourne une nouvelle Wallet
        if (this.balance < price.value()) throw new InsufficientBalanceException();
        return new Wallet(this.balance - price.value());
    }
}
```

<p class="fragment">Le test passe toujours. Le code est meilleur. 🎯</p>

---

## Pourquoi TDD ?

<p class="fragment">👉 Vous ne pouvez pas écrire un test pour un code mal conçu. <strong>TDD force le bon design.</strong></p>
<p class="fragment">👉 Vous savez exactement quand une feature est "finie" : quand le test est vert.</p>
<p class="fragment">👉 La suite de tests est un <strong>filet de sécurité</strong> pour refactoriser sans peur.</p>
<p class="fragment">👉 C'est la base de la <strong>confiance</strong> dans un pipeline CI/CD.</p>
