## 1. BDD : Behavior Driven Development 🥒

<p class="fragment">Le BDD n'est pas une technique de test.</p>
<p class="fragment"><strong>C'est une technique de communication.</strong></p>

---

### Le problème classique 🤦

Le bureau du BDA vous envoie ce message :

> *"Il faut que les étudiants puissent s'inscrire à l'événement."*

---

### Ce que chacun comprend...

<div style="display:flex; gap:1.5em; font-size:0.85em;">
    <div style="flex:1; background:#e3f2fd; padding:1em; border-radius:8px;">
        <strong>🧑‍💼 Le BDA pense :</strong>
        <ul>
            <li>L'étudiant choisit sa place</li>
            <li>Il paie</li>
            <li>Il reçoit un billet nominatif</li>
            <li>S'il annule, la place est remise en vente</li>
        </ul>
    </div>
    <div style="flex:1; background:#fce4ec; padding:1em; border-radius:8px;">
        <strong>👨‍💻 Le Dev code :</strong>
        <ul>
            <li>Un formulaire</li>
            <li>Un bouton "Valider"</li>
            <li>Une ligne en base de données</li>
            <li>Annuler = supprimer la ligne</li>
        </ul>
    </div>
</div>

<p class="fragment" style="margin-top:0.8em; background:#fff3e0; padding:0.8em; border-radius:8px;">
⚠️ Résultat : L'annulation supprime la participation, mais <strong>le stock de places n'est jamais réincrémenté</strong>. 50 places disponibles ? Après 2 annulations : toujours 50 en base, mais 48 réellement libres.
</p>

---

### Pourquoi ce bug existe ?

Pas à cause du code.

<p class="fragment">Parce que <strong>"s'inscrire"</strong> n'a pas le même sens pour tout le monde.</p>
<p class="fragment">Pour le BDA : c'est un <em>contrat</em> (place réservée, paiement, billet).</p>
<p class="fragment">Pour le dev : c'est un <em>enregistrement</em> (une ligne en base).</p>
<p class="fragment">👉 Le BDD oblige à aligner ces deux visions <strong>avant</strong> d'écrire la première ligne de code.</p>

---

### La Solution : Le Gherkin

Un langage compréhensible par le **Métier**, les **Devs** et les **QAs**.

**Fichier : `achat_place.feature`** (Ceci est votre cahier des charges !)

```gherkin
Feature: Achat de place pour le Gala

  Scenario: Un étudiant achète une place avec solde suffisant
    Given l'événement "Gala Hiver" a 50 places restantes
    And l'étudiant "Bob" a 25€ sur son compte
    When "Bob" tente d'acheter une place à 20€
    Then la transaction est validée
    And le solde de "Bob" est de 5€
    And il reste 49 places pour l'événement
```

---

### Du Gherkin au Code (Cucumber)

Ces phrases ne sont pas juste du texte. Elles exécutent du code Java.

```java
@Given("l'étudiant {string} a {int}€ sur son compte")
public void setupStudentWallet(String name, int amount) {
    // Ce code prépare le contexte du test
    walletRepository.save(new Student(name, amount));
}

@When("{string} tente d'acheter une place")
public void attemptPurchase(String name) {
    // Ce code appelle votre VRAIE logique métier
    shotgunService.buyTicket(name);
}
```

<p class="fragment">👉 <strong>Règle :</strong> Si le test Cucumber passe (vert), la feature est finie. Pas avant.</p>

# 2. DDD : Domain Driven Design <!-- .element: class="r-fit-text" -->

---

### La Philosophie DDD

Souvent, on code en pensant "Base de données" :
*   ❌ *"J'ai une table `T_TICKET`, je vais faire une classe `Ticket` avec des Getters/Setters."*

En DDD, on pense "Comportement Métier" :
*   ✅ *"Un `Ticket` ne peut être émis que si le `Paiement` est validé."*

---

### 2a. Ubiquitous Language (Langage Omniprésent) 🗣️

Le problème n°1 des projets n'est pas technique, il est **sémantique**.

Si le métier dit "Shotgun" et le dev code "ReservationRequest", il y a une traduction mentale permanente.
C'est là que naissent les bugs.

---

### L'Exemple du "Billet" 🎫

**Scénario catastrophe :**
- Le BDA : "On doit pouvoir **annuler** un billet." (Sous-entendu : rembourser et remettre en vente).
- Le Dev : `ticket.cancel()` (Met juste le status à 'CANCELLED').
- Résultat : L'étudiant est remboursé, mais la place est perdue à jamais car le stock n'a pas été incrémenté.

**Pourquoi ?** Parce que "Annuler" voulait dire deux choses différentes.

---

### La Règle d'Or du Langage Omniprésent

Le code doit être **lisible** par un expert métier (si on enlève la syntaxe Java).

**❌ Mauvais code :**
`if (u.getBalance() < p.getPrice()) { throw new Exception(); }`

**✅ Bon code (Ubiquitous) :**
`if (etudiant.aUnSoldeInsuffisantPour(soiree)) { throw new SoldeInsuffisantException(); }`

> "Ne traduisez pas le métier en technique. Codez le métier."

---

### 2b. Bounded Contexts (Contextes Bornés) 📦

Un mot peut avoir plusieurs sens selon le contexte. Essayer de faire un modèle "Global" unique est une erreur.

Prenons l'objet **"Étudiant"**.

---

### Le "Polymorphisme Sémantique"

**Dans le contexte "Vente / Shotgun" :**
- C'est un **Acheteur**.
- On s'en fiche de son nom ou promo.
- Seul compte : Son `Solde` et son `Panier`.

**Dans le contexte "Accès / Sécurité" :**
- C'est un **Participant**.
- On s'en fiche de son solde.
- Seul compte : Son `Nom`, `Prénom`, `QR Code valide`.

---

### Une application, Plusieurs Modèles

Au lieu d'une classe `Etudiant` géante de 200 lignes...
On crée des modèles dédiés par contexte.

<img src="../assets/images/diagrams/bounded-contexts.png" alt="Bounded Contexts" style="max-height:450px;">

<p class="fragment">C'est la base de l'architecture Microservices : chaque service a sa propre vision du monde.</p>

# 3. Architecture Hexagonale <!-- .element: class="r-fit-text" -->

(Aussi appelée "Ports & Adapters")

---

### Le problème de l'architecture en couches (MVC classique)

`Controller` ➡️ `Service` ➡️ `Repository` ➡️ `Database`

*   Le Service dépend du Repository.
*   Si je change de Database (ex: SQL vers Mongo), je risque de casser mon Service.
*   Le métier est "pollué" par des annotations techniques (`@Entity`, `@Table`, `@Column`).

---

### La Solution Hexagonale 🏰

On inverse les dépendances. Le **Domaine** (Métier) est au centre, pur et sans framework.

<img src="../assets/images/diagrams/hexagonal-architecture.png" alt="Architecture Hexagonale" style="max-height:500px;">

---

### La Règle d'Or

> "Les dépendances vont toujours de l'extérieur vers l'intérieur."


<div class="r-stack">
<img class="fragment fade-in-then-out" src="https://www.numendo.com/wp-content/uploads/2024/08/Architecture-Hexagonale.png" alt="Dependency Rule" style="max-height:500px;">

<div class="fragment fade-in-then-out">
    <ul>
        <li>Le Domaine ne dépend de rien.</li>
        <li>Le Domaine ne connait RIEN de l'extérieur. (Interdit d'importer `java.sql.*` ou `org.springframework.*` dans le domaine).</li>
    </ul>
</div>
</div>

---

### Concrètement, le code ?

Voici l'arborescence que vous aurez :

```text
/src/main/java/com/bda/shotgun
├── application       <-- Les cas d'utilisation (Orchestration)
│   └── AcheterPlaceUseCase.java
├── domain            <-- LE CŒUR (Pur Java)
│   ├── model         <-- Objets métier (Ticket, Etudiant)
│   └── ports         <-- Interfaces (Contrats)
│       ├── in        <-- Ce que je sais faire (API)
│       └── out       <-- Ce dont j'ai besoin (DB, Mail)
└── infrastructure    <-- LA TECHNIQUE (Spring, SQL)
    ├── adapter       <-- Implémentation des ports (Repository)
    ├── config        <-- Configuration Spring
    └── controller    <-- API REST
```

---

### Focus : Les Ports (Interfaces)

Le Domaine définit des besoins via une interface Java.

**Dans `/domain/ports/out/TicketRepositoryPort.java` :**
```java
package com.bda.shotgun.domain.ports.out;

import com.bda.shotgun.domain.model.Ticket;

// Interface purement métier. Aucune notion de SQL ici.
public interface TicketRepositoryPort {
    void save(Ticket ticket);
    boolean existsById(String id);
}
```

---

### Focus : Les Adapters (Implémentation)

L'Infrastructure implémente l'interface avec la techno de son choix.

**Dans `/infrastructure/adapter/PostgresTicketRepository.java` :**
```java
@Repository // Annotation Spring autorisé ICI seulement
public class PostgresTicketRepository implements TicketRepositoryPort {
    
    // Ici on utilise JPA/Hibernate
    private final JpaTicketDao dao; 

    @Override
    public void save(Ticket ticket) {
        // Mapping Domaine -> Entité BDD
        TicketEntity entity = mapToEntity(ticket);
        dao.save(entity);
    }
}
```

# Découpage Fonctionnel & Équipes <!-- .element: class="r-fit-text" -->

---

## Team 1 : Catalog & Seating 🏟️

**Responsabilité :** La source de vérité sur les événements et les places.

<ul>
  <li>Créer/gérer un événement : <code>DRAFT → OPEN → CLOSED</code></li>
  <li>Définir le plan de salle (zones, rangées, sièges numérotés)</li>
  <li>Exposer la disponibilité en temps réel (verrous Redis)</li>
  <li>Gérer l'ouverture de shotgun à une heure précise</li>
</ul>

**Bounded Contexts :** `Event` / `Venue & Seating` / `Shotgun`

**⚠️ Point d'attention DDD :**
Un `Seat` n'est pas un entier. C'est un agrégat avec un cycle de vie : `AVAILABLE → HELD → BOOKED → RELEASED`.

🔗 **Coopération :** expose l'API de verrou de siège consommée par **Team 2** (REST sync) + consomme `TicketCancelled` de **Team 3** pour libérer une place (async).

---

## Team 2 : Checkout & Reservation 💳

**Responsabilité :** Le tunnel d'achat, de la sélection au paiement.

<ul>
  <li>Initier une commande et poser un verrou temporaire sur le siège</li>
  <li>Gérer l'<strong>expiration automatique</strong> du hold (10 min)</li>
  <li>Intégrer la gateway de paiement (mock Stripe : succès / échec / timeout)</li>
  <li>Confirmer ou annuler la réservation</li>
</ul>

**Bounded Contexts :** `Order` / `Reservation & Hold` / `Payment`

**⚠️ Point d'attention BDD :**
La concurrence est le vrai challenge : 2 étudiants veulent le même siège au même instant. Votre scénario le plus difficile.

🔗 **Coopération :** appelle **Team 1** pour vérifier/verrouiller le siège (REST sync) + publie `OrderConfirmed` → **Team 3** génère le billet (async).

---

## Team 3 : Ticketing & Access 🎟️

**Responsabilité :** La preuve d'achat et le contrôle à l'entrée.

<ul>
  <li>Consommer <code>OrderConfirmed</code> → générer PDF + QR Code unique</li>
  <li>Envoyer le billet par email (Mailpit)</li>
  <li>Scanner le QR à l'entrée : <code>VALID / ALREADY_USED / INVALID</code></li>
  <li>Gérer l'annulation et le transfert de billet entre étudiants</li>
</ul>

**Bounded Contexts :** `Ticket & Delivery` / `Access Control`

**⚠️ Point d'attention Hexa :**
PDF et email sont des Adapters. Votre domaine dit juste : `ticketService.issue(orderId)`.

🔗 **Coopération :** consomme `OrderConfirmed` de **Team 2** (async) + publie `TicketCancelled` → **Team 1** libère la place (async).

---

## Team 4 : Frontend & UX 🎨

**Responsabilité :** L'interface unique étudiants et BDA.

<ul>
  <li>Plan de salle <strong>interactif</strong> (sélection visuelle de siège)</li>
  <li>Tunnel de checkout avec <strong>countdown du hold</strong> (10 min)</li>
  <li>Dashboard admin (créer event, uploader plan, stats ventes)</li>
  <li>Espace "Mes billets" (afficher QR, annuler, transférer)</li>
</ul>

**Techno :** React / Vue / Angular (au choix de l'équipe)

**⚠️ Point d'attention Intégration :**
Vous consommez les APIs des 3 autres équipes. OpenAPI/Swagger est votre contrat. Exigez des **contrats stables** — si une API change sans prévenir, c'est vous qui êtes bloqués.

🔗 **Coopération :** vous êtes le canari dans la mine. Si ça plante chez vous, c'est qu'une API a changé.
