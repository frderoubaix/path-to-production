## 1. BDD : Behavior Driven Development 🥒

<p class="fragment">Le BDD n'est pas une technique de test.</p>
<p class="fragment"><strong>C'est une technique de communication.</strong></p>

---

### Le problème classique

1.  Le métier (BDA) veut : *"Un système juste pour les places".*
2.  Le dev code : *"Si `timestamp_click` < `now`, alors erreur".*
3.  Le résultat : On ne s'est pas compris, le dev a oublié la gestion du panier.

---

### La Solution : Le Gherkin

Un langage compréhensible par le **Métier**, les **Devs** et les **QAs**.

**Fichier : `achat_place.feature`** (Ceci est votre cahier des charges !)

```gherkin
Feature: Achat de place pour le Gala

  Scenario: Un étudiant achète une place avec solde suffisant
    Given l'événement "Gala Hiver" a 50 places restantes
    And l'étudiant "Bob" a 25€ sur son compte
    When "Bob" tente d'acheter une place à 20€
    Then la transaction est validée
    And le solde de "Bob" est de 5€
    And il reste 49 places pour l'événement
```

---

### Du Gherkin au Code (Cucumber)

Ces phrases ne sont pas juste du texte. Elles exécutent du code Java.

```java
@Given("l'étudiant {string} a {int}€ sur son compte")
public void setupStudentWallet(String name, int amount) {
    // Ce code prépare le contexte du test
    walletRepository.save(new Student(name, amount));
}

@When("{string} tente d'acheter une place")
public void attemptPurchase(String name) {
    // Ce code appelle votre VRAIE logique métier
    shotgunService.buyTicket(name);
}
```

<p class="fragment">👉 <strong>Règle :</strong> Si le test Cucumber passe (vert), la feature est finie. Pas avant.</p>

# 2. DDD : Domain Driven Design <!-- .element: class="r-fit-text" -->

---

### La Philosophie DDD

Souvent, on code en pensant "Base de données" :
*   ❌ *"J'ai une table `T_TICKET`, je vais faire une classe `Ticket` avec des Getters/Setters."*

En DDD, on pense "Comportement Métier" :
*   ✅ *"Un `Ticket` ne peut être émis que si le `Paiement` est validé."*

---

### Ubiquitous Language (Langage Omniprésent)

Le code doit parler la langue du métier.

<div style="display: flex; justify-content: center;">
<ul>
    <li>❌ <strong>Tech :</strong> <code>UserHasEventTable</code> <br> 👉 <strong>Métier :</strong> <code>Participation</code></li>
    <li>❌ <strong>Tech :</strong> <code>UpdateRow()</code> <br> 👉 <strong>Métier :</strong> <code>ConfirmerShotgun()</code></li>
    <li>❌ <strong>Tech :</strong> <code>DeleteTicket</code> <br> 👉 <strong>Métier :</strong> <code>RembourserEtudiant</code></li>
</ul>
</div>

> "Si vous utilisez un mot dans le code que le trésorier du BDA ne comprend pas, c'est une <strong>dette technique</strong>."

---

### Bounded Contexts (Contextes Bornés)

Pour éviter le "Plat de spaghettis" géant, on découpe le métier en zones étanches.

# 3. Architecture Hexagonale <!-- .element: class="r-fit-text" -->

(Aussi appelée "Ports & Adapters")

---

### Le problème de l'architecture en couches (MVC classique)

`Controller` ➡️ `Service` ➡️ `Repository` ➡️ `Database`

*   Le Service dépend du Repository.
*   Si je change de Database (ex: SQL vers Mongo), je risque de casser mon Service.
*   Le métier est "pollué" par des annotations techniques (`@Entity`, `@Table`, `@Column`).

---

### La Solution Hexagonale 🏰

On inverse les dépendances. Le **Domaine** (Métier) est au centre, pur et sans framework.

<pre class="mermaid">
flowchart TB
subgraph Drivers [Infrastructure Driver]
    API[Rest Controller]
    CLI[Console APP]
end
subgraph Hexagon [HEXAGONE]
    PortIn([Port In Interface])
    Domain[Domaine Logique Métier]
    PortOut([Port Out Interface])
end
subgraph Driven [Infrastructure Driven]
    DB[(Postgres Adapter)]
    Mail[(Smtp Adapter)]
end
API --> PortIn
CLI --> PortIn
PortIn -.->|Implémente| Domain
Domain --> PortOut
DB -.->|Implémente| PortOut
Mail -.->|Implémente| PortOut
classDef plain fill:#fff,stroke:#333,stroke-width:2px;
class Domain,PortIn,PortOut plain;
</pre>

---

### La Règle d'Or

> "Les dépendances vont toujours de l'extérieur vers l'intérieur."

*   L'infra connait le Domaine.
*   **Le Domaine ne connait RIEN de l'extérieur.** (Interdit d'importer `java.sql.*` ou `org.springframework.*` dans le domaine).

---

### Concrètement, le code ?

Voici l'arborescence que vous aurez :

```text
/src/main/java/com/bda/shotgun
├── application       <-- Les cas d'utilisation (Orchestration)
│   └── AcheterPlaceUseCase.java
├── domain            <-- LE CŒUR (Pur Java)
│   ├── model         <-- Objets métier (Ticket, Etudiant)
│   └── ports         <-- Interfaces (Contrats)
│       ├── in        <-- Ce que je sais faire (API)
│       └── out       <-- Ce dont j'ai besoin (DB, Mail)
└── infrastructure    <-- LA TECHNIQUE (Spring, SQL)
    ├── adapter       <-- Implémentation des ports (Repository)
    ├── config        <-- Configuration Spring
    └── controller    <-- API REST
```

---

### Focus : Les Ports (Interfaces)

Le Domaine définit des besoins via une interface Java.

**Dans `/domain/ports/out/TicketRepositoryPort.java` :**
```java
package com.bda.shotgun.domain.ports.out;

import com.bda.shotgun.domain.model.Ticket;

// Interface purement métier. Aucune notion de SQL ici.
public interface TicketRepositoryPort {
    void save(Ticket ticket);
    boolean existsById(String id);
}
```

---

### Focus : Les Adapters (Implémentation)

L'Infrastructure implémente l'interface avec la techno de son choix.

**Dans `/infrastructure/adapter/PostgresTicketRepository.java` :**
```java
@Repository // Annotation Spring autorisé ICI seulement
public class PostgresTicketRepository implements TicketRepositoryPort {
    
    // Ici on utilise JPA/Hibernate
    private final JpaTicketDao dao; 

    @Override
    public void save(Ticket ticket) {
        // Mapping Domaine -> Entité BDD
        TicketEntity entity = mapToEntity(ticket);
        dao.save(entity);
    }
}
```

# Découpage Fonctionnel & Équipes <!-- .element: class="r-fit-text" -->

---

## Team 1 : Catalog & Shotgun (Le Cœur) 🏟️

**Responsabilité :** Création des événements et gestion du "Shotgun".
- Admin : Créer un event "Gala" avec 200 places.
- User : Voir la liste, voir le décompte avant ouverture.
- **Domaine :** Gestion parfaite du stock.

**⚠️ Point d'attention DDD :**
La notion de "Stock" n'est pas un simple entier en base. C'est un concept critique qui doit être géré avec des règles (ex: "On ne peut pas décrémenter si < 0").

---

## Team 2 : Payment & Wallet 💳

**Responsabilité :** Gestion des flux financiers (fictifs).
- **Service Externe :** Simulation d'une banque.
- **Domaine :** Le "Wallet" de l'étudiant.
    - Règle : *Solde ne peut être négatif.*
    - Règle : *Blocage des fonds avant validation.*

**⚠️ Point d'attention BDD :**
Scenario : "Solde insuffisant". Scenario : "Erreur technique banque".

---

## Team 3 : Ticketing & Access 🎟️

**Responsabilité :** Délivrer la preuve d'achat.
- Génère un PDF unique avec QR Code.
- API REST pour scanner le QR Code à l'entrée.

**⚠️ Point d'attention Hexa :**
La génération de PDF et l'envoi de mail sont des détails d'infrastructure (Adapters). 
Votre domaine dit juste : `notificationService.envoyerBillet(ticket)`.

---

## Team 4 : Frontend & UX 🎨

**Responsabilité :** L'interface unique pour les étudiants et le BDA.
- Dashboard Admin (Création event, Stats ventes).
- Page publique "Shotgun" avec compte à rebours.

**⚠️ Point d'attention Intégration :**
Vous êtes les consommateurs des API Hexagonales des autres. Si le contrat (API) change, tout casse. => Swagger est votre ami.
